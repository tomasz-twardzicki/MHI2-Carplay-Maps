Reference: [`OMKE/wireless-carplay-virtual-cockpit`](https://github.com/OMKE/wireless-carplay-virtual-cockpit/tree/321191526ef26f98df87d85cd35d7597e5940ff1),

are in `OMKE-2026-10-31.json`. This is a static comparison against our current
v3/v3r3 sources and the existing Mini Pico captures, not a test of either dongle.
No adapter firmware, car package or upstream runtime is installed or vendored.
The published local v3r3 ZIP remains unchanged.

## Why this reference matters

The adapter has two independent AirPlay roles: a receiver toward the iPhone and
a sender toward the head unit. A successful command on the car-facing session
does not establish delivery on the phone-facing session. Video and control
forwarding are separate capabilities.

The [technical description](https://github.com/OMKE/wireless-carplay-virtual-cockpit/blob/321191526ef26f98df87d85cd35d7597e5940ff1/docs/HOW_IT_WORKS.md)
describes preserving the car's display advertisement, negotiating `altScreen`,
accepting stream 111 from the phone, and opening a separate stream 111 to the
car. The relay decrypts/re-encrypts video between those sessions; the H.264
content is not decoded/repainted to remove UI elements. Therefore a working
cluster picture establishes a video path, not complete layout-command support.

## Specific clue for the Mini Pico turn card

[`src/altscreen.c`](https://github.com/OMKE/wireless-carplay-virtual-cockpit/blob/321191526ef26f98df87d85cd35d7597e5940ff1/src/altscreen.c)
defines `CLUSTER_MAP_URL` as the plain `maps:/car/instrumentcluster/map`. The
`sink_thread` sends that URL directly to the **phone-facing** session in `showUI`
when its video socket connects. It does not use the car's selected no-overlay
URL or its MU preferences. The shim also initiates its own phone-side keyframe
requests while waiting for an IDR.

The [README's limitations](https://github.com/OMKE/wireless-carplay-virtual-cockpit/blob/321191526ef26f98df87d85cd35d7597e5940ff1/README.md#known-limitations)
and [current research status](https://github.com/OMKE/wireless-carplay-virtual-cockpit/blob/321191526ef26f98df87d85cd35d7597e5940ff1/research/docs/STATUS.md)
explicitly say that car-to-phone cluster commands are not forwarded. The latter
names `updateViewArea`, `forceKeyFrame` and `stopUI` as missing relays. This is a
concrete implementation where cluster video/zoom works while the car's display
controls do not fully propagate.

**Inference for Mini Pico, not a confirmed cause:** it could likewise ignore or
rewrite a car-side scene request, or independently activate a default scene.
That would explain why our map-only base and acknowledged OFF requests coexist
with the visible card. OMKE is a different platform/firmware; these sources do
not prove Mini Pico uses this code or identify which behavior it has. They also
do not prove a plain `/map` URL always produces a card on every app.

The next useful investigation is on the adapter's phone-facing control path:
compare its advertised displays/features/view areas with the car's, check the
cluster UUID mapping between sessions, and observe the actual phone-side
`showUI`/`requestUI` URLs and later overrides. A capture should identify the
producer/session and be collected while Mini Pico is still connected, before
switching to a cable. The existing MU status alone cannot show that forwarding.
Repeating an accepted command or resetting preferences cannot establish it.

OMKE hard-codes the original MHI2Q/MIBSI cluster UUID and 1440×540. Our current
map-only base advertises `b7e6c5a0-1367-4791-8000-000000000001`. A real relay
must either preserve the advertised identity or translate both video and
controls consistently. This is a useful check, not evidence that Mini Pico
hard-codes OMKE's UUID, nor a reason to change ours without a trace.

## Connection lifecycle: what to retain and what not to copy

The reference sends activation from a worker after the phone video socket
connects. Its documentation reports that sending through
`AirPlayReceiverSessionSendCommand` inside SETUP can deadlock due to synchronous
dispatch. Our current core already schedules activation separately, gates it
on readiness, retains session references and serializes completion-bearing
commands. There is no newly demonstrated reason to move a send into SETUP or
add a retry loop.

The reference is not a demonstrated reconnect-recovery implementation. Its
README says reconnect/view-switch behavior is lightly tested. In the inspected
shim, `g_cluster_started` is set once, the car context is global, and phone
session/connection identifiers are overwritten as globals. The shim has no
matching added teardown/reset path for those resources. The status note also
acknowledges a per-SETUP allocation leak. These observations are source-level
limits, not a claim that a specific reconnect failed in the author's vehicle.

Our existing session-epoch checks reject stale completions, reset policy on
session removal/start and retain/release the command's session. The guidance
feed additionally distinguishes reader restarts from producer/model restarts
and clears the previous progress floor on a new generation. Those changes,
including the tested atomic-restart case, remain in v3r3. An adapter's private
phone-side reconnect can still be invisible to the car-facing session unless
the adapter signals it; this reference does not solve that upstream boundary.

## Applicability and current package

OMKE targets the **Smart Box AX1800M / `suding`**, with a particular MIPS Linux
`sdDongle` binary and fixed addresses. The user has an **Ottocast Mini Pico,
build 26101215.6071**; matching hardware, ABI and firmware are not established.
Its supplied updater/firmware is therefore not a Mini Pico patch. Its included
Audi MHI2Q car bundle is also unrelated to our exact MU1367/791 install.

The reviewed shim implements display/video transport, not the iAP2 native
route/lane adapter. It contributes no unused-lane encoding correction. The
current [v3r3 lane-type candidate](../lane-type/INSTALL.md) remains the next
vehicle test for type 1; its Mini Pico card limitation remains explicit. This
review changes documentation only and adds no unit commands, runtime changes,
adapter update or new ZIP.
