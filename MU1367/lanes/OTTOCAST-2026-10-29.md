# Mini Pico: valid Card OFF, wireless card remains visible

The user reports on 2026-10-29 that native guidance now works through the
**Ottocast Mini Pico build 26101215.6071**, and album artwork works over both
cable and wireless. Wireless video still contains a turn card after selecting
OFF, selecting ON/reconnecting, then selecting OFF/reconnecting. This report
does not specify apps, individual lane maneuvers or endurance duration.

Evidence: `cpmap-diag-9560199` from `Logs/adapter turn card`. Input hashes and
numeric evidence are in [OTTOCAST-2026-10-29.json](OTTOCAST-2026-10-29.json).
Private logs/navigation data are not copied into this repository. Extension
identities match recovery `MU1367-recovery-a162c85d6365` and artwork
`MU1367-artwork-f353117dbe5c` over the published lane/settings/native layers.

## The OFF setting reached our video core

| Evidence | Value | Meaning |
| --- | --- | --- |
| Current card envelope | position=3, generation=6, valid CRC | OFF persisted |
| Previous card envelope | position=2, generation=5, valid CRC | Prior ON persisted |
| Runtime preference | preference=3, pref_generation=6, pref_source=1, pref_read=1 | Valid current OFF read |
| Declaration | declared=3 | OFF selected while building the display |
| Policy | epoch=1, ready=1, busy=0, blocked=0, applied=3 | OFF sequence completed locally |
| Last operation | sent_op=3, ack_op=3, token=2, status=0, accepted=1 | Subsequent IDR request acknowledged |
| Display envelope | stream=2, layout=2, valid CRC | 30 fps / IDR5, compact narrow |

The exact policy sets `applied_position` after an accepted successful SCENE
completion. Therefore `applied=3` is evidence that the local OFF scene command
completed, even though the last-operation fields have since been overwritten
by IDR (operation 3). Those last fields alone are **not** a retained `showUI`
acknowledgement. No card first-failure snapshot was exported.

791 OFF uses `maps:/car/instrumentcluster/map` for both `initialURL` and live
`showUI`. Its encoded canvas and safe area remain fixed. The runtime-card
build's READY activation only opens the serialized worker; it does not send
a separate unconditional Card ON scene. The native guidance and artwork
adapters do not select the map scene.

The retained video tail contains 249 other command requests, but **zero**
`showUI` requests/completions or `initialURL` records. It cannot reveal a
later phone-side change, a cached adapter declaration, or whether the URL
reached the iPhone. The stored declaration field records the selected setting;
it is not a capture of what the adapter forwarded.

## Adapter scene handling is the leading hypothesis

The working cable comparison and correctly saved/read/applied OFF state
point toward the adapter forwarding, caching or applying the map-only scene
differently. They do not prove which of those happens. The supplied export
has no trace of the adapter-to-phone control channel.

There are 25 incoming `suggestUI` commands rejected by the stock receiver
with `kNotHandledErr` / HTTP 422. Their URLs/display targets are absent.
They are a separate observation, not evidence that our OFF request failed
or that the stock receiver replaced the URL. Changing their handling without
the missing parameters would be speculative.

A [first-hand report for another adapter](https://github.com/chefranov/mhi2-au37x-carplay/issues/25)
describes receiver success without a forwarded zoom operation and uses a map
URL with explicit hide-card parameters. That supports testing the explicit
scene form; it does not establish Mini Pico behavior or guarantee a fix.
