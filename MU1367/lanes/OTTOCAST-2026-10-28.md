was changed. Numeric evidence and input hashes are recorded in
[OTTOCAST-2026-10-28.json](OTTOCAST-2026-10-28.json); private navigation payloads
and full logs are not copied here.

## Adapter and user-reported sequence

The user identifies the adapter as **Ottocast Mini Pico**, build
**26101215.6071**. They recall that the first export may have been captured
on a direct USB cable after switching away from Ottocast, and another after

A cable capture after an adapter session is consistent with the permanent
HMI error latch described below. That consistency does not establish which
connection first caused the error or whether both sessions share one cause.

## Confirmed permanent error latch in our HMI adapter

`LiveBridge.runProduction()` initializes `error=0` outside its read loop.
Any exception other than the specially handled missing mailbox reaches:

```java
catch (Throwable t) { incoming=null; mode=0; error=1; }
```

Every later iteration skips reading when `error!=0`. There is no path that
clears it during a phone disconnect, a different phone session or recovery of
the native reader. The timer and status continue running, which matches the
captures. A full HMI restart resets this local variable; reconnecting the
phone alone does not. This explains why a prior failure can also suppress
subsequent cable guidance until reboot.

The first capture's nonzero writes show that guidance output was attempted
earlier during that HMI lifetime. The second capture's zero writes show that
it did not reach that point in its recorded lifetime. Directory names and
reused startup PIDs are not enough to assign cable/adapter chronology.

## Exact trigger is not present

Both `latest.bin` files were replayed through the released
`CarPlayMU1367Guidance.jar` (SHA256
`90f12f3b7a92bbdc00671c7698ec967cfa905c28923cb580c36cafc0b73af6ab`),
using the exact MU1367 factory interfaces. All 32 retained events pass
`LiveModel.decode`, and both complete mailboxes pass a fresh `MailboxReader`.
The route messages target component 0x10 and indicate active guidance.

Therefore guidance data is not completely absent in the saved snapshots.
However, only the last sixteen events survive, and the status records only
`error=1`, not the exception class or structural failure location. An earlier
semantic rejection, mailbox transition/invariant failure or another caught
exception cannot be distinguished retrospectively. Fresh-reader replay also
does not reproduce the missing history needed for cross-snapshot checks.
The native reader's invalid counter covers source-read/envelope failures;
it is not a count of semantic Java decoder failures.

## Turn card: separate unresolved issue

On 791, Card OFF is selected through the map-only `initialURL` and subsequent
`showUI` scene commands. This does not depend on the native guidance adapter
having permission to draw BAP arrows. The video logs confirm a working stream
and IDR requests every five frames, but retain only a short tail of video
activity. They contain neither the card preference files nor the initial
scene declaration / card-command request and completion needed here.

These exports cannot establish whether Card ON was saved, whether the
adapter cached or changed the display declaration, or whether the map-only
scene command was accepted and forwarded to the phone. Adapter handling of
the scene is a hypothesis, not a confirmed root cause. Frame delivery and
keyframe acknowledgements do not prove scene-command forwarding.

## Next engineering work

1. Add sanitized, bounded failure diagnostics: reason/exception class,
   mailbox serial/session and structural field identifier, without road or
   destination strings. Preserve the first failure before the ring advances.
2. Replace the permanent latch with controlled recovery for expected
   data/session errors: clear output, rebaseline from a validated mailbox,
   and require fresh post-baseline input before reacquiring guidance. Retain
   strict validation, OEM priority and stale-output clearing. Do not simply
   ignore malformed events or replay a stale route.
3. Reproduce adapter connect, disconnect and return-to-cable sequences, with
   the original failure reason retained. Validate recovery before packaging
   an update; the current logs do not justify a particular decoder relaxation.
4. Capture the card preference plus initial display URL and `showUI` request /
   acknowledgement from both adapter and direct-cable sessions. The adapter
   model/build is now known (Mini Pico, 26101215.6071); label the connection
   explicitly for each new export to establish the comparison sequence.

The current Wireless CarPlay MU selector is a stored future-service interface;
it does not change this parser's recovery behavior or implement adapter
protocol translation.
